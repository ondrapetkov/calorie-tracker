# Tags for Meals and Foods Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Meals get meal-type and ingredient tags, foods get ingredient tags, and the Meals tab, Foods tab, meal editor and diary logging use them to find things fast.

**Architecture:**
- **Built-in vocabulary in code.** The tag list (groups and tags) lives in `src/data/builtinTags.ts`.
- **The owner's tags and groups are synced records** in two new Dexie tables, merged with the built-in list into one `Vocabulary`.
- **Foods store `tagIds`.** Meals store only hand-made tag changes (`addedTagIds`, `removedTagIds`) plus `slots`. A meal's ingredient tags are computed from its ingredients every time it is read (spec §3.6.1).
- **All rules are pure, tested functions** in `src/domain/` (vocabulary, meal tag computation, filtering, ordering, Open Food Facts category guess). The UI only wires them up.

**Tech Stack:** TypeScript (strict), React 19, Tailwind 4, Dexie 4 + `dexie-react-hooks`, Vitest + `fake-indexeddb`.

**Spec:** `docs/superpowers/specs/2026-11-03-tags-design.md`

## Global Constraints

- **Local-first.** Screens read only from Dexie; no network call is needed to show or filter tags.
- **Sync.**
  - Every new synced row carries `id`, `updatedAt`, `deletedAt` and `dirty`.
  - New tables are registered in `entityTables` (`src/sync/engine.ts`) as `tag` and `tag_group`.
  - No Supabase change is needed.
- **Dexie version 3.**
  - Rows written before v3, or synced from an older app, may lack `tagIds`, `slots`, `addedTagIds` and `removedTagIds`. Read them as `[]`.
  - New fields are optional in the TypeScript types for that reason.
- **Meals and foods store tag ids, never names.** Built-in tags are never stored; they are referenced by stable ids (below).
- **Built-in tags and groups cannot be renamed or deleted.**
- **Duplicate names are refused** for tags and groups, compared ignoring case, diacritics and surrounding or double spaces ("kimchi" = " Kimchi ", "Kuře" = "kure").
- **Diary entries are snapshots.** No task touches `LogEntry`.
- **Meal types are the diary slots** (`SLOTS`, `SLOT_LABELS` from `src/domain/nutrition.ts`), with any number per meal and none required.
- **Selections combine like this:**
  - Meal types: **any** of them.
  - Ingredient tags: **all** of the selected ones; a meal may have other tags too.
  - Meal types with ingredient tags: **and**.
  - "Untagged" is exclusive with every other chip.
- **No explanatory text appears for automatically added tags.** A brief highlight only.
- **The UI follows the existing look:** components from `src/components/ui.tsx`, the colour tokens in `src/index.css` (`accent`, `line-strong`, `muted`, `surface-2`), phone-first.
- **The tests are Vitest, run with `npx vitest run`.** They must pass in any time zone. The whole suite and `npm run build` must pass at the end of every task.
- **Commits:**
  - Follow the repository style: an imperative sentence, no `feat:` prefix.
  - End every message with `Co-Authored-By: Claude Opus 5.5 <noreply@anthropic.com>`.

## Review Focus

These are the inputs the spec implies but doesn't spell out that would most likely hurt the owner if they broke. Each has a test in the task named.

1. **Old or foreign rows without the new fields.** A meal or food from before v3, or pulled from a device on the old version, must read as "no tags" and never crash. Tested in Task 2 (domain) and Task 4 (repo).
2. **A deleted custom tag still referenced by meals and foods.**
   - It must disappear everywhere: no blank chip, and no Choose row.
   - The item counts as untagged if nothing else is left.
   - Tested in Tasks 1, 2 and 4.
3. **A custom tag whose group was deleted on another device.** The tag must still be visible, under Extras. Tested in Task 1.
4. **A meal ingredient whose food was deleted** (`item.food === undefined`). Its tags are ignored and nothing crashes. Tested in Task 4.
5. **Near-duplicate names** ("  kimchi ", "KIMCHI", "Kuře" vs "kure", and renaming a tag to a built-in name such as "chicken"). They are refused with the existing tag offered. Tested in Tasks 1 and 4.

  ```ts
  export function findGroupByName(v: Vocabulary, name: string, exceptId?: string): GroupInfo | undefined
  export function searchTags(v: Vocabulary, query: string): TagInfo[]
  export function liveTagIds(v: Vocabulary, ids: readonly string[] | undefined): string[]
  ```

### Task 4: Database v3, sync tables and the repository for tags

**Files:**
- Modify: `src/db/schema.ts`, `src/db/repo.ts`, `src/sync/engine.ts` (`entityTables`)
- Test: `src/db/repo.test.ts` (extend), `src/sync/engine.test.ts` (extend)

**Interfaces:**
- Consumes: `buildVocabulary`, `liveTagIds`, `findTagByName`, `findGroupByName` (Task 1); `effectiveMealTags` (Task 2).
- Produces, in `schema.ts`:
  ```ts
  export interface Tag extends SyncFields { name: string; groupId: string }
  export interface TagGroup extends SyncFields { name: string; sortOrder: number }
  // Food gains:   tagIds?: string[]
  // Meal gains:   slots?: Slot[]; addedTagIds?: string[]; removedTagIds?: string[]
  // AppDB gains:  tags: EntityTable<Tag,'id'>; tagGroups: EntityTable<TagGroup,'id'>
  // version(3).stores({ tags: 'id, updatedAt, dirty', tagGroups: 'id, updatedAt, dirty' })
  ```

- Produces, in `repo.ts`:
  - `MealInput` gains `slots?: Slot[]; addedTagIds?: string[]; removedTagIds?: string[]`.
    - On create, a missing value is saved as `[]`. On update, a missing value leaves the stored one unchanged.
    - This keeps the existing `saveMeal` callers and tests valid.
  - `MealDetail` gains `slots: Slot[]` (`meal.slots ?? []`) and `tagIds: string[]`. `tagIds` is the effective live ingredient tags, in vocabulary order: `liveTagIds(v, effectiveMealTags(...))`, built from the live tag ids of the ingredient foods that still exist.
  - New exports:
    ```ts
    export class TagNameTakenError extends Error { constructor(public existingId: string) }
    vocabulary(): Promise<Vocabulary>
    foodsWithTag(tagId: string): Promise<Food[]>            // live foods carrying it, useCount desc then name
    createTag(name: string, groupId: string): Promise<Tag>  // throws TagNameTakenError
    renameTag(id: string, name: string): Promise<void>      // throws TagNameTakenError; throws Error for a built-in id
    deleteTag(id: string): Promise<void>                    // soft delete; throws Error for a built-in id
    createTagGroup(name: string): Promise<TagGroup>         // sortOrder = highest live + 1; throws TagNameTakenError
    renameTagGroup(id: string, name: string): Promise<void>
    deleteTagGroup(id: string, moveTagsTo: string): Promise<void>  // moves its live tags, then soft-deletes, in one transaction
    ```
  - `entityTables` gains `tag: db.tags, tag_group: db.tagGroups`.
